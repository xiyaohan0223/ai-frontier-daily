1Google 发布 Gemini Decisions API：不生成文字，只给选项打分，$0.10/百万输入▸
11 月 11 日上线，底层是新模型 gemini-decision-1。它不做逐 token 解码，而是对一份共享输入（文本、图像、音频、视频、PDF，最高 256K token）一次性评估最多 1,000 个封闭集问题：是/否（noul）、2–255 个选项的多选、以及有序 rubric 打分，每个答案都附带 0–1 的置信度。模型算力中位 50–100ms、端到端 150–250ms，输入 $0.10/百万 token、输出零计费，官方称在同一组基准上比 Gemini 3.5 Flash-Lite + Interactions API 便宜近 5 倍。Google 内部已在用：Gemini Notebook 拿它做实时模型路由（延迟最高降 40%）、Stitch 快速画布、Google Labs 的 CC 从 200 多个表情里挑一个、Search 用它检测 MCP 工具的对抗行为。
Agent 循环里真正高频的调用不是「写答案」，而是路由、选工具、查合规、给上下文打分——这些只需要一个带概率的判断。做成独立端点意味着三件事：成本从「生成多少 token」变成「输入一次」，延迟可以预算，置信度可以直接当阈值用（低于阈值转人工）。对 Accio 这类交易型 Agent，询盘分诊、类目归属、报价与合规前置检查、工具选择都可以先走决策层，把旗舰模型留给真正需要长文本生成的环节。

2Qwen4-Max-Preview 上线：100 万上下文、单次最多输出 39 万 token▸
11 月 11 日 10:00 开放：官方文档标注上下文 1M、最大输出 393,216 token，原生视觉理解，主打复杂编程、前端设计、专业软件操作与长程 Agent 任务；当前仅 Token Plan 可调用，预览期到 11 月 25 日 24:00，官方未公布参数量与基准。同期双 11 活动里 Qwen4 预览可低至 1–2 折体验，并可领取 30 天免费额度。
上下文决定「能读多少」，输出上限决定「一次能交付多少」。39 万 token 足以一次吐出整套多语言 listing、一份完整合规报告，或一版可运行的前端工程，不必再拆成十几轮拼接——这对 Agent 的「交付单元」设计是实质性变化。预览窗口也提醒团队趁现在压测长输出的稳定性与真实单价，别等转正后再补。

3AWS 开源 Emulator：200+ 服务、代码 100% 由 Agent 写成，团队没写也没审一行▸
11 月 11 日 AWS 发布本地 AWS 模拟器并以 CC0 开源：起点只是 438 个 API 模型的空壳，代码全部由自主 Agent 编写，团队没有手写或逐行评审。做法是三组 Agent 分工——一组写 fidelity 测试、一组找问题、一组修复，一个 issue 对一个 Agent，数百个并发 Agent 每天修掉数千个 issue，合并前要过四道 gate。官方同时公开了「things-that-do-not-work」清单：不模拟限流、宕机与区域差异，也不做沙箱隔离。
这是「Agent 写生产级软件」目前最硬的样本，值得抄的不是规模而是流程：把可验证的测试当作规格、把 issue 当作工作单元、把 merge gate 当作唯一的人工介入点。它也划出了边界——工程正确性可以靠测试逼近，但环境语义（限流、区域、故障）仍必须由人来定义。

1arXiv 2611.14492｜ReTrace：把工具型 Agent 蒸馏成「没有规划器」的工作流▸
业务自动化的本质是把同一套 SOP 反复跑在新输入上，但 Agent 每一轮都要调用 LLM 选择下一步，规模化后延迟与成本都吃不消。ReTrace 用 SOP 加少量运行日志，把 Agent 每次工具调用时写下的「为什么这么做」抽出来，跨多次运行合并成一份紧凑规则文档，再编译成由代码而非 LLM 决定下一步的可执行工作流；只有最后一步依赖平台，因此同一份规则可以编译到不同编排系统。在生产平台的 79 条流程上完成率 93.8%（Agent 为 96.8%），单任务成本低 24%；τ²-Bench 上 75.8% vs 80.6%，但耗时 1.3 秒 vs 170 秒；三轮针对训练失败的修复把 k=2 工作流从 66.7% 提到 81.2%；SOP-Bench 修复后 87.8%、每条 0.40 秒，对比 Agent 的 85.5% / 46.6 秒。
用 3 个百分点的成功率换 100 倍的延迟下降和 24% 的成本，对「高频、低变异」的业务（询盘分诊、单证校验、订单状态流转）几乎是稳赚。更值得抄的是它的中间产物：一份人可读的规则文档——这让 Agent 的行为第一次能被业务方评审、diff 和版本化。

2NeurIPS 2026｜Contrastive Discovery：让发现 Agent 在「互斥解释」之间做实验▸
现有科研 Agent 多是逐点验证假设：只测 h 与 ¬h。证据否掉 h 之后，Agent 只知道「这个解释不太可能」，并不知道证据支持哪个替代方案。本文把单个假设换成「对比集」——一个科学问题加一组互斥且穷尽的竞争解释，每次实验按「证据如何重新分配信念」打分，当信念集中到一个解释上问题即告解决。六个领域里，逐点方法中信念变化最大的候选有 89% 是被否掉的；用同一批证据，对比集能把其中 73% 落到具体替代解释；用对比集引导搜索时，同等实验预算下解决的问题多 67%；38 位人类专家在 78% 的已解决问题上给出同一解释，在「逐点 Agent 否掉就停」的问题上是 82%。
这套东西可以直接搬出实验室：选品失败、投放没效果、询盘转化低，本质上都是「否掉了某个假设但不知道真正原因」。把诊断做成「竞争解释集 + 按证据重分配信念」，比让 Agent 反复猜要可靠得多，也更容易向人解释「为什么换这个方案」。

3arXiv 2611.14326｜When Should Agents Remember：把记忆更新当假设来证伪▸
长时程 Agent 的自改进常把「这一轮的经验」直接写进长期记忆，但局部成功并不等于可复用、安全的知识。FGSE 把每条候选经验表示成结构化假设：显式前提、行为改动、预期效果、验证器；先只在临时状态里生效，通过迁移测试、证伪测试与历史回归测试后，再决定提交、修正还是拒绝。在 web、app、工具使用与长期记忆基准上，WebArena 39.8、AppWorld 平均完成 78.8、τ-Retail/τ-Airline 的 Pass^1 为 0.724/0.487，同时把证伪失败压到 5.0%、回归损伤 1.3%、有害提交 3.6%。
「Agent 越用越聪明」最大的风险是越用越偏。把记忆写入变成一次带验证器的灰度发布，思路和软件上线完全一致——这是目前最工程化的一版记忆治理方案。做长期记忆时至少要回答三个问题：这条经验的前提是什么、怎么证伪、失败了怎么回滚。

4arXiv 2611.13541｜Agent 基准在任务耗尽之前就先失去了区分度▸
作者重新打分八个基准（含 SWE-bench Verified、Terminal-Bench、MLE-bench、ALE-Bench）的已发布运行记录，认为所谓「饱和」很大程度出在测量而非任务：多数基准把一次运行压成一个通过/失败比特。这有两重毛病——粒度太粗，SWE-bench Verified 前十名之间的差距小于测试本身的误差，纠正误差后的重排幅度不超过随机删掉每个 Agent 六分之一通过项；上限被参考值卡住，ALE-Bench 按竞赛分排的前十在对着中位数人类评分时全部打平，尽管近一半运行其实超过了该人类。作者给出带日期锚点的截断对数比评分，并把成本当作独立轴；Terminal-Bench 重跑中，通过率打平的模型在被丢弃的那个量上相差十倍以上。
评测只输出 0/1，团队就会围绕 0/1 优化。把「过了多少、好多少、花多少」分开度量，才能看清模型在长任务上的真实边际。做内部 Agent 评测时，最该抄的是「成本作为独立维度」这一条——否则永远不会有人为降本买单。

5Nature Machine Intelligence｜多模态细胞基础模型：只做「对齐」不够▸
Richter、Zimmermann 与 Crawford 在 11 月 11 日上线的分析中指出，多模态细胞基础模型当前流行的做法是把不同生物模态（转录组、蛋白、影像等）的表征对齐到同一空间，但对齐只解决「可比较」，并不能带来跨模态的协同增益；真正有效的整合需要在预训练目标与架构层面设计模态间的互补与约束。文章分别讨论了「对齐式整合」与「协同式整合」的差别，并给出判断整合程度的标准。
这条结论对多模态 Agent 同样成立：把图片、文本、表格塞进同一个向量空间只是第一步，能不能让一种模态纠正另一种模态的错误，才是「整合」。对商品理解这种天然多模态的场景，值得用同样的标准审视——图文对齐之后，图能不能推翻写错的标题？
